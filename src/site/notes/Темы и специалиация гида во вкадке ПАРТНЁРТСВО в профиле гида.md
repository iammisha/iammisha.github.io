# ТЗ: реорганизация справочника тематик

## 1. Задача

Справочник тематик должен использоваться одновременно в нескольких сценариях платформы:

|Сценарий|Для чего|
|---|---|
|Заявка туриста|турист указывает, что ему интересно|
|Профиль гида|гид указывает свои специализации|
|Поиск гида агентством|агентство ищет гида по тематике|
|Создание экскурсии|гид/агентство назначает экскурсии основную и дополнительные темы|
|Сайт гида/агентства|турист фильтрует экскурсии по тематикам|
|В будущем|автоматическое сопоставление заявки ↔ гид ↔ экскурсии|

Справочник должен быть **единым**, но набор отображаемых элементов может отличаться в разных интерфейсах.

# 2. Что изменить концептуально

Сейчас в `lib_theme` смешаны:

- реальные темы;
- сезонность;
- питание;
- формат;
- слишком узкие гастрономические теги;
- слишком широкие бессодержательные понятия.


# 3. Структура `lib_theme`

Я бы оставил текущую таблицу, но расширил её.

ALTER TABLE lib_theme

``` SQL
    ADD COLUMN parent_id INT NULL,

    ADD COLUMN code VARCHAR(100) NULL,

    ADD COLUMN item_type VARCHAR(20) NOT NULL DEFAULT 'theme',

    ADD COLUMN is_active TINYINT(1) NOT NULL DEFAULT 1,

    ADD COLUMN sort_order INT NOT NULL DEFAULT 0,

    ADD COLUMN redirect_to_id INT NULL;
```


И после миграции:

``` SQL
CREATE UNIQUE INDEX uq_lib_theme_code

ON lib_theme(code);
```


### Поля

|Поле|Значение|
|---|---|
|`id_theme`|текущий внутренний ID|
|`parent_id`|родительская группа|
|`code`|постоянный системный код|
|`name_theme`|название|
|`item_type`|`group` или `theme`|
|`is_active`|доступна ли тема|
|`sort_order`|порядок отображения|
|`redirect_to_id`|куда перенаправлять устаревшую тему|

**Важно:** бизнес-логика API не должна строиться на `name_theme` и желательно не строиться на конкретных числовых ID.

Например:

code = blockade_leningrad

name_theme = Блокада Ленинграда

Название в будущем можно поменять без изменения логики приложения.

# 4. Контексты использования

Не советую делать пять колонок вида:

show_for_tourist

show_for_guide

show_for_excursion

...

Это сначала удобно, но со временем появятся новые сценарии.

Лучше отдельная таблица:


``` sql
CREATE TABLE lib_theme_context (

    theme_id INT NOT NULL,

    context_code VARCHAR(50) NOT NULL,

    is_visible TINYINT(1) NOT NULL DEFAULT 1,

    is_featured TINYINT(1) NOT NULL DEFAULT 0,

    sort_order INT NOT NULL DEFAULT 0,

  

    PRIMARY KEY (theme_id, context_code),

  

    CONSTRAINT fk_theme_context_theme

        FOREIGN KEY (theme_id)

        REFERENCES lib_theme(id_theme)

);
```

Контексты:

tourist_request

guide_profile

excursion_editor

public_excursion_filter

partner_guide_search

Например:

Архитектура

  

tourist_request          visible

guide_profile            visible

excursion_editor         visible

public_excursion_filter  visible

partner_guide_search     visible

А:

Достоевский

  

tourist_request          не featured

guide_profile            visible

excursion_editor         visible

public_excursion_filter  visible

partner_guide_search     visible

# Связь с профилем гида

Если у всех пользователей есть общий `profile_id`, лучше:


``` sql
CREATE TABLE profile_theme (

    profile_id BIGINT NOT NULL,

    theme_id INT NOT NULL,

    is_primary TINYINT(1) NOT NULL DEFAULT 0,

  

    PRIMARY KEY (profile_id, theme_id)

);
```
Это позволит в будущем использовать тематики не только для гида, но и для агентства.


# Поиск партнёра-гида

Здесь единый справочник начинает давать большую пользу.

Например агентство ищет:

Язык: английский

Тематика: Достоевский

Дата: 14 сентября

Поиск работает по:

profile_theme

Причём можно ранжировать:

Достоевский is_primary = 1      → максимальный балл

# 26. API

Я бы попросил разработчика не отдавать фронтенду просто весь `lib_theme`.

Пример:

GET /api/library/themes?context=tourist_request

или:

GET /api/library/themes?context=guide_profile

Ответ:

[

``` json
  {

    "id": 100,

    "code": "architecture_city",

    "name": "Архитектура и город",

    "type": "group",

    "children": [

      {

        "id": 101,

        "code": "architecture",

        "name": "Архитектура"

      },

      {

        "id": 102,

        "code": "courtyards_entrances",

        "name": "Дворы и парадные"

      }

    ]

  }

]
```
Таким образом фронтенд вообще не знает, какие категории надо скрывать — это контролируется БД.

## Что получится в итоге

Это позволит использовать **одни и те же данные во всей платформе**:

Турист
«Интересует архитектура и Достоевский»
          ↓
Заявка получает theme_id
          ↓
Агентство открывает заявку
          ↓
Поиск партнёров
          ↓
Система находит гидов с этими specialization theme_id
          ↓
Гид имеет экскурсии с теми же theme_id
          ↓
Можно предложить подходящие готовые экскурсии
